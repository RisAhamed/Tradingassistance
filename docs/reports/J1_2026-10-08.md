# Phase J.1 — Evidence-derived poll window + engine-poll observation

## a. Phase summary

Phase J.1 closes the direct-mode measurement gap left by Phase J: the
harness sync wait is now governed by a validated, evidence-derived
`poll_window_seconds` (shipped: 60s), and every wait runs the engine's own
continuous resync loop alongside the harness poll, with first-seen
timestamps recorded on both sides plus a `pass_deferred_fill` outcome for
fills the engine catches after the harness window. Ten real Alpaca paper
runs produced ten fills: six observed in-window at ~2.3–2.4s, four
confirmed present only after the old 30s window (all under 60s). Two real
bugs found in live evidence were fixed (exit fills never reached the
ledger during flatten verification; the verdict used `flatten()`'s stale
intermediate return). Pipeline mode was started twice and killed by the
developer (local hardware heat); it has NOT completed and is deferred to
CI per the agreed plan.

## d. Code changes (unified diff per file)

`app/acceptance/direct.py`:
- `_poll_terminal(broker, engine, order, ...)` now also calls
  `engine._resync_orders_from_broker()` every iteration and returns
  `(status, polls, last_error, harness_first_seen)`; per-poll structured
  log includes broker_order_id/status/filled/poll#/error.
- `run_direct` subscribes to `ORDER_FILLED` for the order before the wait
  (engine-first-seen proof); wait budget is
  `min(poll_window_seconds, timeout)`; ambiguous branch runs a bounded
  3-round engine catch-up and, on a caught fill, falls through to the
  FILLED path with outcome `pass_deferred_fill` (exit 0); final verdict
  uses post-verification states (`broker_zero and local_flat and ok`),
  recording `flatten_returned` separately.
- `_await_flat` runs `engine._resync_orders_from_broker()` each round
  (mirrors the live tick loop; without this, exit fills observed only at
  the broker never reach the local ledger — BUGFIX 1).

`app/acceptance/pipeline.py`: order wait uses `poll_window_seconds`;
subscribes to `ORDER_FILLED` for the engine-observed proof; records
`flatten_returned`; verdict on final states.

`app/acceptance/reporting.py`: schema gains `engine_poll_observed_fill`,
`engine_poll_first_seen_at`, `harness_sync_first_seen_at`,
`fill_latency_seconds`, `poll_window_seconds`, `poll_count`,
`poll_error_count`; `OUTCOMES` gains `pass_deferred_fill`.

`app/acceptance/__main__.py`: `--poll-window` / `--poll-interval`
in-process overrides.

## g. The two bug fixes

**BUGFIX 1 — exit fills never reached the ledger during flatten verification.**
Symptom (run 115351Z): entry filled, exit SELL submitted and filled at
the broker (broker ended flat), but `FLATTEN INCOMPLETE remaining:
0.000997499` on all 3 attempts and local stayed long — nothing ran the
engine fill bridge after `flatten()` returned, so the exit fill existed
only broker-side. Change: `_await_flat` now calls
`engine._resync_orders_from_broker()` each round (exactly what the live
tick loop does). Proved by: runs 115658Z–115852Z, all exit 0 with
`final_local_flat true` and `reconciliation ok`.

**BUGFIX 2 — verdict used flatten()'s stale intermediate return.**
Symptom (run 115519Z): flatten OK + reconcile OK in the report, yet
`RESULT: FLATTEN_FAILED (exit 5)` — `engine.flatten()` returns from its
0.5s settle loop before slow fills land. Change: verdict computed from
final verified states (`broker_zero and local_flat and ok`),
`flatten_returned` recorded separately. Proved by: the same four runs
would now exit 0; no code path depends on the intermediate return.

  (all live fills landed in-window once the window was 60s+).
